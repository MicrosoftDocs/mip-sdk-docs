Running Fuzz Test

  1. From MIP repo, unzip "&lt;MipRepo&gt;\scripts\fuzzer\jackalopeFuzzer.7z (this is precompiled https://github.com/googleprojectzero/Jackalope/ fuzzer. It also contains "fuzzing_tests" which is file inputs used by the following python script). 2. Copy &lt;MipRepo&gt;\scripts\fuzzer\jackalopeRunner.py into the extracted folder (should be alongside fuzzer.exe) 3. Compile MIP with "scons -j 8 --configuration=release --arch=x86" (x86 is needed for the fuzzer, you can use x64 with an additional fuzzer flag, but it would be slow) 4. Copy environment.json (the file containing MIP test users. You should take it from the MIP e2e) into the fuzzer directory [<strong>please make sure later when tests are running that you don't get errors for missing environment.json file</strong>. You should look at stdout.txt under fuzzing_results - see below]. 5. Run command 'python jackalopeRunner.py "<MipRepo>\bins\release\x86"' (You need Python 3.5.x Installed). Please wait for the fuzzing to complete. It will take some time (<strong>you can see under "out" folder that new &lt;PREFIX&gt;_modified files are created and its modified time is changing which is a good sign</strong>, also you can see under "fuzzing_results" inside the "stdout.txt" of the current test the prints as explained in "checking crashes". Note that you will also see some of the MIP errors inside the console, it is normal). You can always exit fuzzing by clicking CTRL+C, and later, when you rerun the cmd in step (5) it will resume the fuzzing test from the last time (it will also show you the results so far if you rerun the fuzzer. If you want to start from scratch, delete "session.dat" which will reset the fuzzing script state. WARNING: this will also delete "fuzzing_results"). 6. When everything finishes, you will see the results for each test. Pay attention to the <strong>crashes</strong> [the fuzzer does not save hangs, only say they occurred. It possible to recompile the fuzzer to save the hangs as well. But crashes are the real security issues]. 7. <strong>You advised to run the sanity test to make sure you did everything correctly, see below.</strong> @subsection autotoc_md9 Checking Crashes 1. Under the fuzzer directory, you will see the results in "fuzzing_results". 2. For example, in "fuzzing_results\docx\Apply label" you will see the test results for "docx" file type for "Apply label" operation. 3. Under that folder, you will have "stdout.txt" file which will show you the fuzzer (and MIP's) output. 4. **Under "fuzzing_results\docx\Apply label\out\crashes" you will see the input that causes the crash (NOTE: each file that causes crash is named along the lines of "access_violation_00000000xxxxx936_0000000000000000_1". You should change the file name and add the extension according to the test name - in this case ".docx", and this is the problematic file!**. You can even debug it without the fuzzer sample program - In my case, when I found a real issue, opening it in AIP Right-Click caused a crash too..). NOTE: The name of crash might indicate if it a new one or a duplicate crash input, but, you probably want to check it manually with procdump (and if that's a duplicate, attach all of the duplicate inputs to the bug you open - there might be few reasons for a crash in specific line) NOTE: Hangs does not result in input files that caused them. This is a limitation of Jackalope fuzzer. The behavior can be changed by editing the fuzzer code itself and recompile it. However, that does not seem to be necessary as hangs are mostly because we are doing some network calls and in addition hangs are not exploitable security vulnerabilities which is probably why Jackalope does not treat them as important (so they are not interesting for the SDL as well). @subsection autotoc_md10 Running Crash Without The Fuzzer (but with the same fuzzer "sample program") 1. <strong>Let's say we got crash named</strong> "access_violation_00000000xxxxx936_0000000000000000_1" (see step (4) from Checking Crashes). 2. Copy this file into "<MipRepo>\bins\release\x86"' 3. Copy environment.json into "<MipRepo>\bins\release\x86"' as well (see above) 4. If we got that crash in "docx" file type and "Apply Protection" test we will run (from MIP's bin folder): 'fuzzing_tool.exe "<MipRepo>\bins\release\x86" "access_violation_00000000xxxxx936_0000000000000000_1" "docx" 2' 5. You need to replace "access_violation_00000000xxxxx936_0000000000000000_1" into the input file name, replace "docx" into input file type, and replace "2" into number of test operations. In our case, "Apply Protection" is operation number 2. <tt>operations = {"Apply label": 0, "Delete Label": 1, "Apply Protection": 2, "Remove Protection": 3} (from python script)</tt> 6. You probably should run this after you registered Procdump as default debugger (search how to do it in the internet, so you will get the crash dump) @subsection autotoc_md11 Sanity Test (Did I do everything right?) 1. Edit "src\file\api_impl\file_handler_impl.cpp" file. 2. In "void FileHandlerImpl::SetLabel" function, after the "label == nullptr" check, add the following (This should crash the program if the first buffer of .txt file is "d" or "SOH" [look at ascii table]): @icode uint8_t bufferr = 0; mFileItem->GetStream()->Read(&bufferr, sizeof(bufferr)); if (bufferr == 100 || bufferr == 1) { char * pp = 0; *pp = 'f'; MIPLOG(TRACE) << "something!"; throw NotSupportedError("something!"); } @endicode 3. Compile MIP (as explained above). 4. Edit "fuzzing_test" folder, and delete everything inside. 5. Create "txt" folder inside. 6. Create a "1.txt" file which contain "abd" text (we expect fuzzer to get the wrong input on his own). 7. Edit jackalopeRunner.py file (in fuzzer directory), and remove all tests, and put just one test: <tt>tests = [("Apply label", "txt", timedelta(hours=2))]</tt> 8. Run fuzzer python script as explain above 9. You should see at least 2 crashes. When you edit the crashes files you will see one have "d" as the first char and the other have "SOH" as the first char (anything else may vary). 10. <strong>NOTE: Remember to revert jackalopeRunner.py changes and revert "fuzzing_test" changes (and also delete session.dat).
